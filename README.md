# Employee Requests API

REST API для управления сотрудниками, отделами и внутренними заявками сотрудников.

Проект разработан на **FastAPI**, **PostgreSQL** и **SQLAlchemy 2.0** с использованием асинхронного доступа к базе данных. Приложение разделено на слои API, репозиториев, сервисов, схем и моделей.

## Возможности

- Управление отделами
- Управление сотрудниками
- Управление заявками сотрудников
- CRUD-операции
- Назначение автора и исполнителя заявки
- Установка дедлайна заявки
- Автоматическая генерация номера заявки
- Управление статусами заявок
- Проверка допустимых переходов между статусами
- Асинхронная работа с PostgreSQL
- Миграции базы данных через Alembic
- Swagger-документация API
- Автоматические тесты с pytest

## Статусы заявок

Для заявок реализована логика переходов между статусами:

```text
CREATED
├── IN_PROGRESS
│   ├── DONE
│   └── CANCELLED
└── CANCELLED
```

Допустимые переходы:

```text
CREATED     → IN_PROGRESS
CREATED     → CANCELLED
IN_PROGRESS → DONE
IN_PROGRESS → CANCELLED
```

Статусы `DONE` и `CANCELLED` являются конечными.

Попытка выполнить недопустимый переход отклоняется приложением.

## Основные сущности

### Department

Отдел компании.

### Employee

Сотрудник компании, относящийся к определённому отделу.

### Request

Внутренняя заявка сотрудника.

Заявка содержит:

- уникальный номер;
- описание;
- дедлайн;
- статус;
- автора;
- исполнителя.

Номер заявки генерируется автоматически в формате:

```text
REQ-001
REQ-002
REQ-003
```

## API

Основной префикс API:

```text
/api/v1
```

Основные ресурсы:

```text
/api/v1/departments
/api/v1/employees
/api/v1/requests
```

API позволяет создавать, получать, изменять и удалять отделы, сотрудников и заявки.

Для заявок также предусмотрен отдельный endpoint изменения статуса с проверкой допустимости перехода.

После запуска приложения интерактивная документация Swagger доступна по адресу:

```text
http://127.0.0.1:8000/docs
```

OpenAPI-схема:

```text
http://127.0.0.1:8000/openapi.json
```

## Установка

Клонируйте репозиторий:

```bash
git clone https://github.com/Iridium111/-employee-requests.git
cd -employee-requests
```

Создайте виртуальное окружение:

```bash
python -m venv .venv
```

Активируйте его:

### Linux / macOS

```bash
source .venv/bin/activate
```

### Windows

```bash
.venv\Scripts\activate
```

## Переменные окружения

Для подключения к PostgreSQL необходимо настроить переменные окружения в `.env`.

Пример:

```env
DB_USER=postgres
DB_PASSWORD=postgres
DB_NAME=employee_requests
DB_HOST=localhost
DB_PORT=5433
```

Значения необходимо изменить в соответствии с локальной конфигурацией.

## Запуск PostgreSQL через Docker

В проекте используется Docker Compose для запуска PostgreSQL.

Запуск:

```bash
docker compose up -d
```

Проверка запущенных контейнеров:

```bash
docker compose ps
```

Остановка:

```bash
docker compose down
```

Данные PostgreSQL сохраняются в Docker volume.

## Миграции базы данных

Для управления схемой базы данных используется Alembic.

Применить все миграции:

```bash
alembic upgrade head
```

Посмотреть текущую миграцию:

```bash
alembic current
```

Создать новую миграцию после изменения ORM-моделей:

```bash
alembic revision --autogenerate -m "migration description"
```

## Архитектура

Проект разделён на несколько слоёв:

```text
HTTP Request
     ↓
FastAPI Router
     ↓
Service Layer
     ↓
Repository Layer
     ↓
SQLAlchemy
     ↓
PostgreSQL
```

**Routers** отвечают за обработку HTTP-запросов и формирование ответов.

**Schemas** используются для валидации входящих и исходящих данных с помощью Pydantic.

**Services** содержат бизнес-логику приложения, например правила изменения статусов заявок.

**Repositories** отвечают за взаимодействие с базой данных.

**Models** описывают таблицы и связи между сущностями с помощью SQLAlchemy ORM.

Такое разделение позволяет отделить HTTP-логику, бизнес-правила и работу с базой данных друг от друга.
