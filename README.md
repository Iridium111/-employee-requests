# Employee Requests API

REST API для управления отделами, сотрудниками и внутренними заявками компании.

Проект разработан на **FastAPI**, **PostgreSQL** и **SQLAlchemy 2.0** с использованием асинхронного доступа к базе данных. Архитектура приложения разделена на API, сервисный и репозиторный слои.

## Возможности

- CRUD-операции для отделов;
- CRUD-операции для сотрудников;
- CRUD-операции для заявок;
- назначение автора и исполнителя заявки;
- установка дедлайна;
- автоматическая генерация номера заявки;
- управление жизненным циклом заявки;
- проверка допустимых переходов между статусами;
- валидация статусов с помощью `Enum`;
- асинхронная работа с PostgreSQL;
- миграции базы данных через Alembic;
- автоматическая документация OpenAPI / Swagger;
- автоматические тесты с помощью pytest.

## Статусы заявок

Для управления жизненным циклом заявки используется конечный автомат состояний (State Machine).

```text
CREATED
├── IN_PROGRESS
│   ├── DONE
│   └── CANCELLED
└── CANCELLED
```

Допустимые переходы:

```text
CREATED     → IN_PROGRESS
CREATED     → CANCELLED
IN_PROGRESS → DONE
IN_PROGRESS → CANCELLED
```

Статусы `DONE` и `CANCELLED` являются конечными.

Допустимые значения статусов определены с помощью `Enum`. Передача неизвестного статуса отклоняется на этапе валидации входных данных.

Попытка выполнить переход между существующими статусами, который не разрешён State Machine, отклоняется бизнес-логикой приложения.

## Основные сущности

### Department

Отдел компании.

### Employee

Сотрудник компании, относящийся к определённому отделу.

### Request

Внутренняя заявка сотрудника.

Заявка содержит:

- уникальный номер;
- описание;
- дедлайн;
- статус;
- автора;
- исполнителя.

Номер заявки генерируется автоматически в формате:

```text
REQ-001
REQ-002
REQ-003
```

## API

Основной префикс API:

```text
/api/v1
```

Основные ресурсы:

```text
/api/v1/departments
/api/v1/employees
/api/v1/requests
```

API позволяет создавать, получать, изменять и удалять отделы, сотрудников и заявки.

Для заявок предусмотрен отдельный endpoint изменения статуса с проверкой допустимости перехода.

После запуска приложения интерактивная документация Swagger доступна по адресу:

```text
http://127.0.0.1:8000/docs
```

OpenAPI-схема:

```text
http://127.0.0.1:8000/openapi.json
```

Клонируйте репозиторий:

```bash

cd -employee-requests
```

Создайте виртуальное окружение:

```bash
python -m venv .venv
```

Активируйте его.

```bash
source .venv/bin/activate
```

### Windows

```bash
.venv\Scripts\activate
```

## Переменные окружения

Для подключения к PostgreSQL необходимо настроить переменные окружения в `.env`.

Пример:

```env
DB_USER=postgres
DB_PASSWORD=postgres
DB_NAME=employee_requests
DB_HOST=localhost
DB_PORT=5433
```

Значения необходимо изменить в соответствии с локальной конфигурацией.

## Запуск PostgreSQL через Docker

Для запуска PostgreSQL используется Docker Compose.

Запуск контейнеров:

```bash
docker compose up -d
```

Проверка запущенных контейнеров:

```bash
docker compose ps
```

Остановка:

```bash
docker compose down
```

Данные PostgreSQL сохраняются в Docker volume.

## Миграции базы данных

Для управления схемой базы данных используется Alembic.

Применить все миграции:

```bash
alembic upgrade head
```

Посмотреть текущую миграцию:

```bash
alembic current
```

Создать новую миграцию после изменения ORM-моделей:

```bash
alembic revision --autogenerate -m "migration description"
```

## Архитектура

Приложение разделено на несколько слоёв:

```text
HTTP Request
     ↓
FastAPI Router
     ↓
Service Layer
     ↓
Repository Layer
     ↓
SQLAlchemy
     ↓
PostgreSQL
```

**Routers** отвечают за обработку HTTP-запросов, вызов необходимой логики и формирование HTTP-ответов.

**Schemas** используются для валидации входящих и исходящих данных с помощью Pydantic.

**Services** содержат бизнес-логику приложения, в частности правила изменения статусов заявок.

**Repositories** отвечают за взаимодействие с базой данных через SQLAlchemy.

**Models** описывают таблицы базы данных и связи между сущностями с помощью SQLAlchemy ORM.

Такое разделение позволяет отделить HTTP-логику, бизнес-правила и работу с базой данных друг от друга.
