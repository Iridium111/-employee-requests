# Employee Requests API

REST API для управления отделами, сотрудниками и внутренними заявками компании.

Проект разработан на **FastAPI**, **PostgreSQL** и **SQLAlchemy 2.0** с использованием асинхронного доступа к базе данных.

Приложение построено на многослойной архитектуре **Router → Service → Repository**, которая позволяет разделить обработку HTTP-запросов, бизнес-логику и взаимодействие с базой данных.

## Возможности

### Управление данными
- CRUD-операции для отделов;
- CRUD-операции для сотрудников;
- CRUD-операции для заявок;
- назначение автора и исполнителя заявки;
- установка дедлайнов;
- автоматическая генерация номера заявки;
- проверка существования связанных сущностей.

### Управление заявками
- управление жизненным циклом заявки;
- реализация State Machine;
- проверка допустимых переходов между статусами;
- валидация статусов с помощью `Enum`;
- обработка ошибок бизнес-логики.

### JWT-аутентификация
- проверка логина и пароля;
- хранение хешей паролей;
- генерация Access Token и Refresh Token;
- обновление пары JWT;
- ротация Refresh Token;
- выход из системы;
- отзыв Refresh Token при выходе;
- проверка подписи и срока действия JWT;
- обработка ошибок аутентификации.

### Инфраструктура
- асинхронная работа с PostgreSQL;
- миграции базы данных через Alembic;
- запуск PostgreSQL через Docker Compose;
- автоматическая документация OpenAPI / Swagger;
- автоматические тесты с использованием pytest.

## Архитектура

Приложение разделено на несколько слоёв:

```text
HTTP Request
     |
     v
FastAPI Router
     |
     v
Service Layer
     |
     v
Repository Layer
     |
     v
SQLAlchemy ORM
     |
     v
PostgreSQL
```

### Router Layer

Отвечает за:
- обработку HTTP-запросов;
- валидацию входных данных;
- вызов сервисов;
- формирование HTTP-ответов.

### Service Layer

Содержит бизнес-логику приложения:
- проверку допустимых переходов между статусами;
- аутентификацию пользователей;
- проверку JWT;
- обновление и отзыв refresh-токенов.

### Repository Layer

Отвечает за взаимодействие с PostgreSQL:
- получение записей;
- создание сущностей;
- изменение данных;
- удаление записей;
- сохранение refresh-токенов.

### Models

SQLAlchemy ORM-модели описывают таблицы базы данных и связи между сущностями.

### Schemas

Pydantic-модели используются для валидации входящих и исходящих данных.

## Основные сущности

### Department

Отдел компании.

Используется для организации сотрудников по подразделениям.

### Employee

Сотрудник компании, относящийся к определённому отделу.

### Request

Внутренняя заявка сотрудника.

Содержит:
- уникальный номер;
- описание;
- дедлайн;
- статус;
- автора;
- исполнителя.

Номер заявки генерируется автоматически:

```text
REQ-001
REQ-002
REQ-003
```

### User

Учётная запись пользователя.

Содержит:
- UUID пользователя;
- логин;
- email;
- хеш пароля;
- refresh token;
- связь с сотрудником.

Используется для аутентификации пользователей.

## Жизненный цикл заявки

Для управления статусами реализован конечный автомат состояний — **State Machine**.

```text
CREATED
├── IN_PROGRESS
│   ├── DONE
│   └── CANCELLED
└── CANCELLED
```

### Допустимые переходы

| Текущий статус | Новый статус |
|---|---|
| CREATED | IN_PROGRESS |
| CREATED | CANCELLED |
| IN_PROGRESS | DONE |
| IN_PROGRESS | CANCELLED |

Статусы `DONE` и `CANCELLED` являются конечными.

Неизвестные значения статусов отклоняются на этапе валидации входных данных.

Недопустимые переходы между существующими статусами отклоняются бизнес-логикой приложения.

## JWT-аутентификация

Для аутентификации пользователей используются **JSON Web Tokens (JWT)**.

Система работает с двумя типами токенов.

### Access Token

Используется для доступа к защищённым ресурсам API после подключения проверки авторизации к соответствующим эндпоинтам.

Содержит:
- UUID пользователя;
- тип токена;
- время окончания действия.

### Refresh Token

Используется для получения новой пары токенов без повторного ввода логина и пароля.

Активный Refresh Token сохраняется в PostgreSQL.

При обновлении токенов сервер проверяет, совпадает ли переданный Refresh Token с сохранённым в базе данных.

### Эндпоинты аутентификации

Основной префикс:

```text
/api/v1/auth
```

| Метод | Endpoint | Описание |
|---|---|---|
| POST | `/login` | Вход пользователя |
| POST | `/refresh` | Обновление JWT |
| POST | `/logout` | Выход из системы |

### Login

**POST `/api/v1/auth/login`**

Пример запроса:

```json
{
  "login": "developer",
  "password": "example_password"
}
```

При успешной аутентификации сервер возвращает:

```json
{
  "access_token": "<access_token>",
  "refresh_token": "<refresh_token>"
}
```

HTTP-статус:

```text
200 OK
```

### Refresh

**POST `/api/v1/auth/refresh`**

Пример запроса:

```json
{
  "refresh_token": "<refresh_token>"
}
```

Алгоритм обновления токенов:

1. Проверка подписи и срока действия JWT.
2. Проверка типа токена.
3. Получение UUID пользователя из JWT.
4. Поиск пользователя в PostgreSQL.
5. Сравнение Refresh Token с сохранённым в базе данных.
6. Генерация новой пары Access Token и Refresh Token.
7. Сохранение нового Refresh Token.
8. Возврат новой пары токенов клиенту.

После успешной ротации предыдущий Refresh Token больше не принимается, если новая строка токена отличается от предыдущей.

### Logout

**POST `/api/v1/auth/logout`**

Пример запроса:

```json
{
  "refresh_token": "<refresh_token>"
}
```

После проверки токена сервер удаляет сохранённый Refresh Token из PostgreSQL.

Успешный ответ:

```text
204 No Content
```

После выхода пользователь больше не может обновлять авторизацию с помощью отозванного Refresh Token.

Ранее выданный Access Token остаётся действительным до окончания срока действия.

### Обработка ошибок аутентификации

Приложение обрабатывает следующие ситуации:

- неверный логин или пароль;
- недействительный JWT;
- истёкший Refresh Token;
- неверный тип токена;
- использование отозванного Refresh Token;
- отсутствие пользователя.

Для ошибок аутентификации используется HTTP-статус:

```text
401 Unauthorized
```

## Установка и запуск

### 1. Клонирование репозитория

```bash
git clone https://github.com/Iridium111/-employee-requests.git
cd -employee-requests
```

### 2. Создание виртуального окружения

```bash
python -m venv .venv
```

Активация на Linux / macOS:

```bash
source .venv/bin/activate
```

Активация на Windows:

```bash
.venv\Scripts\activate
```

### 3. Установка зависимостей

Установите зависимости проекта в соответствии с конфигурацией `pyproject.toml`.

### 4. Настройка переменных окружения

Создайте файл `.env` в корневой директории проекта.

Пример переменных PostgreSQL:

```env
DB_USER=postgres
DB_PASSWORD=postgres
DB_NAME=employee_requests
DB_HOST=localhost
DB_PORT=5433
```

Для JWT необходимо настроить секретный ключ и алгоритм подписи.

Пример:

```env
JWT_SECRET_KEY=replace_with_secure_random_secret
JWT_ALGORITHM=HS256
```

Названия параметров и сроки действия токенов должны соответствовать конфигурации приложения.

**Важно:** не добавляйте `.env` и реальные секретные ключи в Git.

### 5. Запуск PostgreSQL

Для запуска PostgreSQL используется Docker Compose.

```bash
docker compose up -d
```

Проверка контейнеров:

```bash
docker compose ps
```

Остановка:

```bash
docker compose down
```

Данные PostgreSQL сохраняются в Docker volume.

### 6. Применение миграций

```bash
alembic upgrade head
```

### 7. Запуск FastAPI

```bash
uvicorn app.main:app --reload
```

После запуска приложение доступно по адресу:

```text
http://127.0.0.1:8000
```

Swagger UI:

```text
http://127.0.0.1:8000/docs
```

|---|---|
